# Documentation website

The site in `website/` combines the Arveld landing with Astro and Starlight
documentation. It builds static HTML for `arveld.com`; serving it does not require
a Node server, an application database or a controller.

## Run and build

Use Node.js compatible with [package.json](../../website/package.json) and npm:

```sh
cd website
npm ci
npm run dev
```

Open [localhost:4177](http://127.0.0.1:4177/). The landing is at `/`, and the
documentation begins at `/docs/`.

```sh
npm run build
npm run preview
```

From the repository root, `task website:install` and `task website:build` run
the same locked installation and production build used by CI.

The production build writes **`dist/client/`**. Pagefind search is generated by
the build; check it with `npm run preview`. Building and previewing do not publish
the site.

## Publish to Cloudflare

Cloudflare Workers Static Assets serves the landing at [arveld.com](https://arveld.com)
and the documentation at [/docs/](https://arveld.com/docs/). The
[`wrangler.jsonc`](../../website/wrangler.jsonc) configuration deploys the
`arveld-website` Worker with static files only. It preserves directory index
routing, adds trailing slashes to HTML routes and serves the generated `404.html`
with a 404 status for unknown paths. It has no application server, database or
SPA fallback. Cloudflare manages DNS and TLS for the custom domain.

After a release is published, [`release.yml`](../../.github/workflows/release.yml)
calls [`website.yml`](../../.github/workflows/website.yml) with its version. This
includes prereleases. The website is built from that tag's commit, using the
locked npm dependencies. The workflow checks the tag signature, published
immutable release, main ancestry and successful main CI and frontend audit for
that commit before deployment. A direct reusable workflow call also works for
releases created with `GITHUB_TOKEN`, which do not trigger a separate
`release: published` workflow.

Configure these repository Actions values:

| Kind | Name | Value |
| --- | --- | --- |
| Variable | `CLOUDFLARE_ACCOUNT_ID` | Account owning `arveld.com` |
| Secret | `CLOUDFLARE_WEBSITE_API_TOKEN` | Dedicated Cloudflare Workers deployment token |

Scope the token to the owning account and the `arveld.com` zone. It needs
Account → Workers Scripts → Edit, Account → Account Settings → Read,
Zone → Workers Routes → Edit and Zone → Zone → Read. Store it only in GitHub
Actions secrets; never copy a local Wrangler OAuth session into CI. The token
is provided only to the deployment step. Installer publication uses its own
token and R2 bucket, described in [installer hosting](installer-hosting.md).

For the first publication or a documentation-only update, deploy validated
`main` without creating an application release:

```sh
gh workflow run website.yml --ref main
```

Manual runs on other branches are rejected. This command requires successful
main CI and frontend audit runs for the selected commit. Deployments are
serialized. Each deployment verifies the public landing, documentation, search
asset, 404 response and `/deployment.json` revision. To retry a failed release
deployment, rerun only its failed website job; the immutable release remains
intact. Replaying an older release deliberately replaces the current website.

To validate the Cloudflare configuration locally after building:

```sh
cd website
npm run deploy:check
```

CI runs this dry run without Cloudflare credentials. Maintainers can also run
`npm exec wrangler login`, set `CLOUDFLARE_ACCOUNT_ID`, then `npm run deploy`
from a validated checkout when manual recovery is necessary. See
[Cloudflare Static Assets](https://developers.cloudflare.com/workers/static-assets/)
and [Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/).

## Browser security headers

[`public/_headers`](../../website/public/_headers) is copied into the static build
and applied by Cloudflare to the website's responses, including the 404 page.
It disables MIME sniffing, embedding the site in frames, browser plugins, and
unused camera, microphone, location, payment and USB permissions. Cross-origin
requests disclose only the site's origin in the referrer. The enforced Content
Security Policy also restricts document base URLs and form submissions to the
same origin.

A separate `Content-Security-Policy-Report-Only` header evaluates a more
restrictive resource policy without blocking resources. Violations appear in
the browser console; no reporting endpoint or telemetry collection is configured.
Inline scripts and styles are currently allowed for Astro, React and Starlight,
and `wasm-unsafe-eval` allows Pagefind's WebAssembly search engine without allowing
JavaScript `eval`. This is not a strict policy against script injection. Before
enforcing resource restrictions, check the landing tour, documentation search,
code copying and Cloudflare-injected resources on the deployed site. A stricter
inline-script policy requires build-generated hashes or nonces.

Astro's development and preview servers do not apply Cloudflare's `_headers`
rules. To inspect the production headers locally after `npm run build`, use:

```sh
npm exec wrangler dev -- --local --ip 127.0.0.1 --port 8787
```

Check the landing, a documentation page and a missing path with `curl -I`, then
review the browser console and interactions. Keep the Cloudflare HSTS setting
at the zone level. These website headers do not configure the separate R2
installer host, Bot Fight Mode, or email DNS records.

## Edit content once

All user and developer documentation is maintained as Markdown under `docs/`:

| Directory | Content |
| --- | --- |
| `docs/guides/` | Installation, product workflows and instance operation |
| `docs/reference/` | Concepts, product usage, results and account settings |
| `docs/develop/` | Source builds, architecture, frontend, verification and this website |

The root README is a short project entry point. Component directories do not
maintain separate READMEs. Keep operator guides about running Arveld; source
compilation belongs in developer documentation. Describe available artifacts
accurately until release downloads and Docker images are published.

[`src/docs/catalog.mjs`](../../website/src/docs/catalog.mjs) selects published
Markdown sources and supplies their routes, titles, descriptions and sidebar
groups. Add a page there to publish it. The content loader reads these files
directly, with no copied content tree.

Write user procedures as UI paths with the exact visible button and field names.
Illustrate the important steps with real product screenshots and label example
data. Do not document Arveld API calls, endpoint tables, request payloads or
curl examples here; the API reference will be a separate OpenAPI page. Keep
necessary host commands for installation, configuration, backups and updates,
where there is no equivalent action in the interface.

Use one H1, then H2/H3 headings. Starlight supplies the rendered page title, so
the Markdown transform removes the source H1. Ordinary Markdown requires no
front matter or MDX components. Keep links relative to the source document:
the transform converts published-document links to site routes and code links
to repository URLs. Files under `website/public/` resolve to public assets.

Keep documentation focused on current behavior. Use Git history for earlier
designs and investigations; do not add roadmap, exploratory or dated QA reports
to the documentation tree. Record verification results with the change they
validate, rather than maintaining a running results document.

## Preserve the product identity

The landing is rendered by Astro and hydrated as a React component for its
screenshot tour. Documentation uses Starlight navigation, search, code-copy
buttons and page contents, with Arveld's palette, mark and local fonts.

`src/brand.css` is generated from `web/src/theme.ts`. The logo comes from
`web/public/favicon.svg`. Local Inter/Manrope fonts and their licenses are copied
from the product's installed Fontsource packages. After installing the product
web dependencies, refresh the website assets from `website/`:

```sh
npm run sync:brand
```

English comes first. Add French content and Starlight locale configuration when
translations are available. Describe concrete uptime-monitoring capabilities
for homelabs and small teams, using the product's Agent and Monitor terminology.

## Verify changes

Build the site, inspect generated links, and review desktop, tablet and mobile
layouts. Check the landing tour, documentation navigation, code copying and
production search. Landing and documentation changes use this workflow without
an automated test suite. Product verification remains separate.
